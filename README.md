# chinook-agent

Агент, що відповідає українською на питання про дані в SQLite-базі Chinook: сам дивиться схему, пише SQL, виправляє помилки й повертає відповідь. Цикл написаний вручну поверх OpenAI-сумісного API, без фреймворків оркестрації. Оцінка на 50 задачах трьох рівнів з еталонами, які рахуються виконанням SQL у базі.

## Як працює

Агент має три інструменти:

| Інструмент | Що робить |
|---|---|
| `get_schema(table?)` | Колонки, первинні й зовнішні ключі однієї або всіх таблиць |
| `run_sql(query)` | Виконує один SELECT у read-only з'єднанні |
| `final_answer(text)` | Завершує роботу й повертає відповідь |

Один крок дорівнює одному виклику моделі, ліміт 8 кроків на питання. Помилка SQL приходить моделі як результат інструмента, тож вона може виправити запит. Якщо модель відповіла текстом без виклику інструмента, цикл приймає це як відповідь.

## Захист від запису

`run_sql` захищений трьома незалежними шарами, бо агенту довіряти не можна:

1. Файл відкривається як `mode=ro` з `PRAGMA query_only`.
2. Токенізатор SQL пропускає лише один запит, що починається з SELECT або WITH. Після CTE основним запитом має бути SELECT, а `;` усередині рядка чи коментаря не вважається роздільником.
3. Авторизатор SQLite відкидає на рівні рушія все, крім читання.

Додатково: `LIMIT 100` додається, якщо його немає, результат обрізається до 100 рядків із прапорцем `truncated`, а виконання переривається за 5 секунд, навіть якщо запит завис у рекурсивному CTE.

## Швидкий старт

Потрібен Python 3.11 або новіший.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

curl -L -o data/Chinook_Sqlite.sqlite \
  https://github.com/lerocha/chinook-database/raw/master/ChinookDatabase/DataSources/Chinook_Sqlite.sqlite

python build_eval.py
pytest -q
```

База не входить до репозиторію. `build_eval.py` створює `data/tasks.jsonl`: 17 задач `single`, 17 `join` і 16 `aggregate`. Без бази тести каталогу пропускаються, решта працює на мінімальній фікстурі.

## Запуск з моделлю

Потрібен провайдер, який підтримує `tools` у `/chat/completions`. Назва моделі не задана за замовчуванням.

```bash
cp .env.example .env
# впиши LLM_API_BASE, LLM_API_KEY, LLM_MODEL
set -a; source .env; set +a   # .env не читається автоматично

python ask.py "Скільки альбомів у Iron Maiden?" --trace
python eval.py
python eval.py --levels single --limit 5
```

`--trace` виводить у stderr весь транскрипт: виклики інструментів, SQL і результати. Без налаштованої моделі `ask.py` виходить з кодом 1, а `eval.py` з кодом 2 і нічого не рахує.

## Оцінка

Еталон кожної задачі обчислюється виконанням `gold_sql` у базі, модель для цього не потрібна. Побудова падає, якщо еталон порожній, обрізаний лімітом або містить NULL.

Відповідь агента звіряється за значеннями, а не за текстом: числа з допуском, рядки без урахування регістру й лапок. Задача розв'язана, коли в відповіді є всі значення еталону. Строгий варіант додатково вимагає, щоб у відповіді не було чисел поза еталоном і питанням.

Рівні задач:

- `single`: одна таблиця, лічильники й прості вибірки;
- `join`: з'єднання двох і більше таблиць;
- `aggregate`: групування, `HAVING`, суми й рейтинги. Там, де можлива нічия, правило її розв'язання записане в самому питанні.

Метрики: частка розв'язаних за рівнями, середня кількість кроків і викликів інструментів, частка задач, що вичерпали ліміт кроків, частка SQL-запитів з помилкою, вартість і затримка задачі. Результат лягає в `results/metrics.md`, `results/eval_<час>.json` і `results/details_<час>.jsonl` з повним транскриптом кожної задачі.

**Чисел з реальною моделлю поки немає.** Тестувалась лише механіка: на локальному моку, що відповідає еталонним SQL, усі 50 задач розв'язуються, а вартість збігається з ручним розрахунком. Це перевіряє оцінювач і клієнт, а не якість жодної моделі. Вартість з'явиться після того, як у `config.yaml` вписано `price_per_1m_input` і `price_per_1m_output`.

## Конфігурація

Параметри лежать у `config.yaml`: ліміт рядків і таймаут SQL, кількість кроків, параметри моделі, допуски порівняння чисел. Змінні середовища перекривають файл:

| Змінна | Призначення |
|---|---|
| `LLM_API_BASE`, `LLM_API_KEY`, `LLM_MODEL` | Провайдер і модель |
| `CHINOOK_DB` | Шлях до файлу бази |
| `CHINOOK_CONFIG` | Шлях до іншого конфігу |

## Структура

```
ask.py             одне питання до бази
build_eval.py      50 задач з еталонами з бази
eval.py            метрики агента
chinook_agent/     SQL-захист, база, інструменти, клієнт, цикл, порівняння, метрики
tests/             125 тестів, мережа й модель не потрібні
docs/DESIGN.md     рішення, відкинуті альтернативи, відомі режими відмови
```

## Відомі обмеження

- Порівняння за значеннями зараховує відповідь, що містить правильне число серед багатьох зайвих. Строга частка це ловить, основна метрика ні.
- Число з трьома знаками після крапки, наприклад «39.624», читається як тисячі.
- Цикл не обмежує кількість однакових помилок SQL поспіль.
- Одна помилка провайдера без токенів у відповіді (наприклад 500) робить вартість усього прогону «не виміряно».
- Каталог задач перевірено на стандартній збірці Chinook; інша збірка може дати порожній еталон.
